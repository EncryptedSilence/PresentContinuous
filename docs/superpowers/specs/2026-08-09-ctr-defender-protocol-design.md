# Refined measurement protocol: complete-CTR defender, split attacker, provenance harness

Branch `measurement-protocol-v2`. Supersedes the measurement protocol behind
`results/speed.csv`, `results/speed-arm.csv`, `results/wide-speed-arm.csv`,
`results/m4-speed.csv` and `results/gpu-speed*.csv` — it does not delete them.

## The problem this fixes

Every defender number in the repository today measures a *round function*, not a
cipher doing work. Three consequences, all of which change published figures:

1. `avx2-bs`, `neon-bs` and `bitslice*-bs` assume the state is **already
   bitsliced**. They are a kernel ceiling, not achievable throughput on
   byte-oriented data. On the M4 the transpose is explicitly outside the timed
   region; on CUDA it is inside the kernel. The same column name means two
   different operations on two targets.
2. The headline question — "how many Mbit/s of video can this device handle" —
   is not what any row answers, so "does the STM32F407 clear 12 Mbit/s" cannot
   be answered from the tables at all.
3. Winners are chosen by the same noisy measurements that are then published.
   Among near-equal kernels this systematically selects whichever got lucky.

## Scope

In: the defender harness, the three CPU targets, the CUDA attacker split, and
the provenance harness that produces all of it. Out: everything Vivado — no
XCV80 place-and-route, no replication sweep, no attack-loop periphery. The one
FPGA item recorded here is the operation-parity requirement (§8), to be executed
later on its own spec.

---

## 1. Provenance harness (cross-cutting)

One driver, `tools/campaign.py`, with a subcommand per target:

```
python3 tools/campaign.py x86  [--tune | --measure]
python3 tools/campaign.py a7   --host <ssh-host> [--tune | --measure]
python3 tools/campaign.py m4   [--tune | --measure]
python3 tools/campaign.py cuda [--tune | --measure]
```

Each run populates `results/v2/<target>/`:

| file | content |
|---|---|
| `env.json` | commit SHA and dirty flag; compiler version and the **verbatim command lines**; flags; CPU/GPU model; governor; pinned frequency; kernel version; sha256 of every measured binary |
| `kat.json` | KAT verdict for each (cipher, impl) that will be measured |
| `runs.csv` | one row per individual run: run index, position in that run's randomised order, cipher, impl, metric, temperature and frequency before and after |
| `tuning.json` | the frozen winner selection; committed separately (§4) |
| `summary.csv` | medians and intervals, generated by `tools/summarize.py` from `runs.csv` |

`tools/make_tables.py` turns `summary.csv` into `paper/tables/*.tex`. No number
reaches a table by hand. This is a hard rule: the mismatched-revision problem
that `results/m4-speed.csv` documents in its own header is exactly what manual
transfer produces.

The driver refuses to run against a dirty tree for the inputs that can change a
measured byte (`Makefile`, `bench/`, `src/`, `include/`, `fw/`), following the
precedent already in `tools/run_m4_bench.py`.

### Disposition of existing results

New files under `results/v2/`. The existing CSVs stay in place and gain a header
line `SUPERSEDED by results/v2/<file>: this file measured the round function,
not a complete CTR operation.` `artifact-manifest.json` describes both sets and
marks which is current.

## 2. The defender workload

One logical workload, identical on x86-64, Cortex-A7 and Cortex-M4:

- **64 KiB** of plaintext, processed **in place**. In-place is what streaming
  CTR code does, and it keeps the three platforms literally identical. On the
  STM32F407 it is also the only variant with headroom: separate 64 KiB input and
  output buffers would need the output in CCM, evicting the runtime-built lookup
  tables into SRAM and leaving the 64 KiB CCM exactly full, with input and output
  then sitting in memories with different wait states.
- One key, expanded **once, before** the timed region. Its cost is measured
  separately and reported in its own column: for a video session this is a
  once-per-session cost, but it is not free and it is not hidden.
- Big-endian counter from zero: 64-bit for the five 64-bit constructions,
  128-bit for the two 128-bit ones.
- 64- and 128-bit ciphers process the **same number of bytes**, not the same
  number of blocks.

Inside the timed region: generate counters, encrypt them, materialise the
keystream as bytes, XOR into the buffer, store. The buffer is `uint8_t *`; no
stage may assume a non-byte representation of the input or output.

Also measured, at 4 KiB and 16 KiB as well as 64 KiB. 64 KiB is the published
size; the other two exist so that `tools/summarize.py` can assert the ranking
does not change with working-set size. A ranking that flips between sizes is a
result about cache, not about ciphers, and the summarizer must say so rather
than leave it to be noticed.

## 3. Defender harness implementation

New file `bench/ctr_bench.c` plus a backend interface header
`bench/ctr_backend.h`. `bench/bench_main.c` is **not modified** — it becomes the
kernel-ceiling harness and its output moves to the secondary artifact.

The interface header is defined in the first task and frozen, because it is what
lets the backend implementations be written in parallel in separate files
(`src/present_ctr_avx2.c`, `src/present_ctr_neon.c`, `src/present_ctr_bitslice.c`,
`bench/wide_ctr_neon.h`, …). Splitting by ISA is a deliberate design choice, not
housekeeping: it is what makes §11's parallel waves possible.

### Backends

Each is a complete CTR implementation, never a round function.

- `ctr-ref` — reference, one block at a time.
- `ctr-table`, `ctr-table-xN` — table-driven, N blocks at a time.
- `ctr-bitslice-u64`, `-u32`, `-avx2`, `-neon` — **counters are generated
  directly in bitsliced representation**, the cipher runs bitsliced, the result
  is transposed back, XORed with the plaintext and stored. **The transpose is
  inside the timed region.**

Generating bitsliced counters directly is cheap, and that is what makes this
both honest and close to the achievable ceiling. For `L` lanes carrying
consecutive counters `c … c+L-1`, the bitsliced form of the low `log2(L)` bits is
a fixed constant pattern independent of `c`; the high bits are a broadcast of
`c`'s bits, and a carry crosses the boundary exactly once per group. That is
about 64 word stores per group rather than a full transpose. A real CTR
implementation would do precisely this.

### Correctness gate

Every backend must reproduce `ctr-ref`'s ciphertext byte for byte over the whole
64 KiB buffer, checked before any timing. Failure aborts the campaign; no
partial results are written.

### Two published defender results

- **Main table** — complete CTR throughput, Mbit/s, from `results/v2/<target>/summary.csv`.
- **Secondary artifact** — `results/v2/kernel-ceiling-<target>.csv` from
  `bench_main.c`, with the header stating: *round function with the state
  already bitsliced; not attainable on byte-oriented data; not comparable with
  the main table.*

This is what stops 416 Mbit/s on the Cortex-A7 being read as a byte-buffer
figure, and what makes the STM32F407's 12 Mbit/s verdict answerable in the mode
that matters.

## 4. Tuning and measurement are separate campaigns

Selection bias is removed structurally, not by care.

**Phase A — tuning.** `--tune` runs every (cipher, backend) combination, 5 runs,
and picks the winner per cipher by median. It writes
`results/v2/<target>/tuning.json` containing the chosen impl per cipher **and
the tuning medians that justified it**, and that file is committed. The choice
is auditable, not merely asserted.

**Phase B — measurement.** `--measure` reads `tuning.json` and refuses to run if
it is missing or names an impl that no longer exists. Only the frozen winners
are measured. These are the numbers that reach the paper.

## 5. Cortex-A7 campaign

Reachable over SSH from the development machine, so the driver does rsync →
build on the board → campaign → collect raw CSVs, and "one reproducible command"
is literal.

- **25 whole-program runs.**
- Within each run, all seven ciphers are measured, and **the order of the seven
  is a fresh random permutation per run**, drawn from a recorded seed.
- Frequency and die temperature are read before and after each cipher and
  written to `runs.csv`.
- A run is discarded and retaken if the clock leaves the pinned 1296 MHz or the
  temperature crosses a configured ceiling. The discard is logged, not silent.

### Statistics

`tools/summarize.py` publishes, per cipher, the median Mbit/s with a **bootstrap
95% CI** (10 000 resamples, seeded).

**Paired ratios are the primary comparison.** Within each run, every cipher's
throughput is divided by `present-80-r16`'s throughput from that same run; the
published figure is the median of those ratios with its own bootstrap CI.
Thermal drift common to a run largely cancels, so absolute speed may wander 10%
while `PRESENT-lin444/PRESENT` holds to 1–2% — and then the ordering is
defensible statistically rather than by assertion.

**Top-group rule.** When a cipher's CI overlaps the leader's, the ciphers are
reported as a top group and not ranked. This is a function in the summarizer
with the overlap test in code, not a sentence in the prose. It is what replaces
the current ranking of 416 / 366 / 353 Mbit/s, and it retires the vague
"~15% variation".

## 6. x86-64: wall-clock as the primary metric

Same `ctr_bench.c`, same tune → freeze → measure structure. Primary metric is
bytes divided by elapsed `CLOCK_MONOTONIC`, reported as Mbit/s. Invariant TSC is
good for repeatability but is not core cycles; it stays as a secondary
diagnostic column labelled *nominal TSC ticks, not core cycles*. All three CPU
targets then share one concept in the main table: bytes processed over actual
time.

### Machine control — three variables the current protocol does not manage

Surveying the measurement machine (i9-14900HX) turned up three uncontrolled
variables, each of the same order as the effects being measured:

1. **`governor = powersave`.** `docs/measurement-environment.md` states plainly
   that this is a record of the machine's defaults rather than a chosen setting.
   With wall-clock as the primary metric it is no longer tolerable.
2. **Core choice.** The part is heterogeneous: CPUs 0–15 are eight P-cores,
   CPUs 16–31 are sixteen E-cores at 4100 MHz. Within the P-cores, CPUs 8–11
   (physical cores 4 and 5) are the favoured cores at **5800 MHz**; the rest cap
   at 5600. The existing `taskset -c 2` lands on a 5600 MHz core — a 3.6%
   handicap that no column records.
3. **Hyperthread sibling.** CPU 2 shares its physical core with CPU 3. Anything
   scheduled there during a trial halves the result, and it appears as an
   outlier rather than as an artifact.

**Assumption, to be confirmed:** the x86 campaign runs with
`governor=performance`, pinned to **CPU 8** with **CPU 9 kept idle**, in a quiet
session with the desktop browser and editor closed. `isolcpus=8,9 nohz_full=8,9`
on the kernel command line is optional and would require a reboot. If a quiet
session on this machine is unacceptable, the alternative is to measure x86 on a
dedicated machine and keep this one for development — at the cost of one more
platform in the provenance record.

`env.json` records the governor, the pinned CPU, whether the sibling was idled,
and whether `isolcpus`/`nohz_full` are active — recorded as observed facts, never
asserted.

## 7. Cortex-M4: fixed hot-code layout

DWT measurement is already very good. What it does not control is placement: the
repository found up to **7.5%** dependence on where the code sits relative to the
128-bit flash fetch boundary. That must stop being a function of which unrelated
routine happened to precede the cipher in the image.

- A dedicated section `.timed`, `aligned(16)`, holding the CTR kernel and
  everything inlined into it.
- `fw/m4/link/product.ld` places `.timed` at a **fixed absolute flash address**,
  ahead of `.text`, so its address does not depend on the rest of the image.
- `tools/campaign.py m4` builds one **minimal firmware per (cipher, winning
  impl)** — extending the per-cipher image split from commit `840b230` — with
  every image's timed section at that same address.
- Post-link assertion via `arm-none-eabi-nm`: the timed symbol must sit at the
  expected address in every image, or the build fails.

**The product configuration (flash + ART) is the defender result.**
`flash-noart` and `sram-noart` move to a separate architectural-experiment CSV
whose header states they are not defender performance.

**Statistics.** DWT is effectively deterministic, so a statistical CI would be
theatre. Publish instead the measurement resolution and a bound on residual
layout sensitivity, the latter obtained from a deliberate experiment linking the
same kernel at successive 16-byte offsets.

Derived headline: Mbit/s at the measured core clock, with an explicit pass/fail
against the 12 Mbit/s requirement — in the real mode, not inside the kernel.

## 8. CUDA attacker: two distinct tasks

The current benchmark is a good **fixed-key block-evaluation** benchmark: key
expansion outside, one pre-expanded key for the whole batch. It is named that
way from now on, because that is what it measures and the repository already
says so.

**Kernel 1 — block evaluation.** All seven constructions. Metric: **block
evaluations/s**. The budget column becomes **block evaluations in 4 h**. This
alone corrects the meaning of Table 5 without any new arithmetic.

**Kernel 2 — master-key search.** Each thread takes its own candidate master
key, runs the key schedule, encrypts a known plaintext and compares the
ciphertext. Metric: **master-key candidates/s**. PRESENT uses the standard
80-bit schedule; AES uses the AES-128 schedule.

The cipher-D family is **excluded** from kernel 2, and the exclusion is written
into the CSV header rather than left to the prose: those variants use
independent round-key material, so no comparable master-key schedule exists.
Forcing all seven rows into a master-key search would be inventing a mapping
that the constructions do not have. Cross-construction comparison is therefore
block evaluation with supplied round-key material; master-key search is a
separate, smaller comparison covering only the constructions where the mapping
is actually defined.

---

## 9. FPGA — recorded, not executed

Everything Vivado is out of scope here. What this spec records for the next FPGA
task: bring all seven cores to identical conditions by synthesising a
**pre-expanded-key** PRESENT variant, so PRESENT performs the same operation as
the other six, while keeping the existing master-key PRESENT as a second,
separately-labelled core — the practically meaningful PRESENT attacker core.
Candidate search is counted without the cost of checking the ciphertext. This
removes the present asymmetry without discarding a useful result.

## 10. Terminology

`tests/s` is retired throughout. The attacker table says **block evaluations/s**,
and the budget column says **block evaluations in 4 h**. **Master-key
candidates** appear only for the genuine full-search kernel of §8.

## 11. Task decomposition and parallelism

Development parallelises; measurement does not. The constraint is not core
count — the development machine has 32 threads — but that this one machine is
simultaneously the x86 target, the CUDA target, the build machine and a desktop.

| # | task | depends on |
|---|---|---|
| 1 | CTR harness, provenance skeleton, frozen `ctr_backend.h`, x86 ref/table backends | — |
| 2 | `ctr-bitslice` for the five 64-bit ciphers: avx2, u64, u32 | 1 |
| 2′ | `ctr-bitslice-neon` for the five 64-bit ciphers | 1 |
| 3 | NEON bitslice for AES and AES-lin444 (ARMv7) | 1 |
| 4a | summarizer: bootstrap CI, paired ratios, top-group, ranking-stability assert, TeX generator | 1 |
| 4b | x86 campaign, tune → freeze → measure | 2, 3, 4a |
| 5 | Cortex-A7 campaign over SSH | 2′, 3, 4a |
| 6a | M4 build infrastructure: `.timed`, fixed address, `nm` assertion, per-impl image | — |
| 6b | M4 campaign and layout-sensitivity experiment | 1, 6a |
| 7 | CUDA split: block evaluation / master-key search | — |

Waves:

```
Wave 1   1 ∥ 7 ∥ 6a
Wave 2   2 ∥ 2′ ∥ 3
Wave 3   4a ∥ 5-driver ∥ 6b-driver
Wave 4   MEASUREMENT — no parallelism
           A7 campaign ∥ M4 campaign      (separate boards, host idle)
           ──── then a quiet machine, nothing else running ────
           x86 campaign
           CUDA campaign
```

The A7 board and the STM32 are separate hardware and the host merely waits on
them, so those two campaigns overlap freely and may overlap with local
development. The x86 campaign is exclusive against everything local: a
concurrent build in another session invalidates it directly. The CUDA campaign
loads the CPU as well as the GPU — and the GPU already carries desktop load —
so it is serial with the x86 campaign.

### Task 3 risk, recorded in advance

ARMv7 NEON has sixteen 128-bit registers and a 64-bit integer datapath, while a
bitsliced 128-bit AES state is 128 lanes × 128 bits = 2 KiB and will spill
heavily. The NEON bitslice may well lose to the table path. That is a legitimate
measured result, not a failed task, and the spec says so beforehand so that the
outcome cannot be quietly reinterpreted afterwards.

## 12. What each target must produce

Per target — x86, A7, M4, CUDA — one reproducible command yielding: commit SHA,
toolchain and flags, frequency and governor, temperature where it applies,
binary hash, KAT verdict, every individual raw run, and an automatically derived
summary CSV. The paper's tables are generated from those CSVs.
