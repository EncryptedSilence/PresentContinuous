1. **Major — The zero-wait model misprices ordinary stores and ignores address dependencies.**  
   `chacha_ascon/tools/arm_cycles.py:117–124` prices an immediate-offset `STR` at two cycles unless preceded by a load. The M4 TRM describes that store as one cycle under the stated unstalled conditions, with completion overlapping subsequent execution. Conversely, the model discounts `ldr r0,[r1]; ldr r1,[r0]` to three cycles despite the address dependency, and omits the additional stall for an address generated by the preceding ALU instruction. These errors can cancel during calibration and change direction between implementations.  
   **Fix:** track destination registers, address operands, addressing modes, and relevant instruction alignment. Model the TRM’s dependency and store-buffer rules explicitly. The existing three-cycle `LDRD/STRD` and `1+N` multiple-transfer costs are appropriate for unstalled accesses. [Arm TRM, §3.3.3](https://documentation-service.arm.com/static/5fce431be167456a35b36ade)

2. **Major — “Flash+ART” omits flash data accesses and their interaction with instruction fetch.**  
   `chacha_ascon/tools/arm_cycles.py:144–170,307–310` models instruction fetches only. Literal loads and other reads from flash retain their zero-wait core prices; the wrapper’s compiled constant-loading `LDRD`s are one concrete example. The model also lacks D-Code cache behavior and bus contention. Consequently, **46.0 → 46.0** for `armv7m_small` means this fetch approximation adds no appreciable stalls; it does not establish zero flash overhead on STM32F407.  
   **Fix:** either call this an *instruction-fetch-only sensitivity model*, or model memory placement, effective data addresses, flash data caching, and arbitration against instruction fetch. Validate its assumptions against [ST RM0090](https://www.st.com/resource/en/reference_manual/dm00031020-stm32f405415-stm32f407417-stm32f427437-and-stm32f429439-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

3. **Major — The calibration does not justify a transferable +0…+10% error band.**  
   `chacha_ascon/tools/calib/m4_present_calib.c:1–7,29–44`; `results/m4-speed.csv:284–289`.  
   Relative to the supplied estimates, measured results require corrections of approximately **+5.2%, +9.4%, +3.0%, +3.5%, and +22.5%**, respectively. Bitslice64 already exceeds the proposed band. Calling the band applicable to “ALU-dominated” code needs an independently specified classification; selecting kernels after observing their residuals would be circular. Moreover, `results/m4-speed.csv:216` documents alignment sensitivity up to 7.5%, and the calibration comment incorrectly says the hardware working set was 4 KiB: the results identify **2048 bytes**, matching this harness.  
   **Fix:** correct the provenance comment; compare actual compiler flags, objects, layouts, memory placement, and timed operations. Validate both model variants against held-out hardware kernels spanning the relevant instruction mixes and multiple code alignments. Until then, report calibration residuals as observations, not a prediction interval. The one-sided bound is particularly unsupported because finding 1 includes overestimation.

4. **Major — There is no enforced KAT gate before publishing cycle results.**  
   `chacha_ascon/arm/Makefile:86–101`.  
   `cycles` depends on `bench_arm.elf`, not a successful `test`; `cycles-flash` inherits this omission. A broken implementation can therefore produce a successful CSV without passing correctness tests. The recipe also discards QEMU’s exit status through the bare `wait`, so emulator failure is not reliably propagated.  
   **Fix:** require successful tests for the same build configuration before estimation, capture and check both process statuses, and publish the CSV only after complete trace/label validation.

5. **Minor — QEMU’s trace includes condition-failed instructions.**  
   `chacha_ascon/tools/arm_cycles.py:4–12,294–312`.  
   I confirmed that the existing binary’s startup `ITE GT` produces trace entries for **both** `ldrgt` and `movle`, although only one executes. The estimator charges every entry according to its opcode. A condition-failed load would receive a load cost and become a fictitious pipelining predecessor; a condition-failed branch would still disrupt the predecessor classification. I found no conditional memory instructions in the sampled measured regions for `m4-asm`, `armv7m_small`, and `bi32_armv7m`, so this is a model correctness gap rather than a demonstrated large error in those particular numbers.  
   **Fix:** obtain condition outcomes/flags, or explicitly model predication and reject traces whose outcomes cannot be resolved.

6. **Minor — Several control-flow costs are approximations presented too strongly as TRM costs.**  
   `chacha_ascon/tools/arm_cycles.py:115–140`.  
   Every preceding two-byte instruction qualifies an IT instruction for folding, including a taken branch into the IT instruction. That is insufficient to establish folding. `TBB/TBH` are also charged like ordinary branches despite their additional table-load/add work, and `LDR PC` receives four cycles despite the TRM’s stated minimum of five. Fixed `P=2` is an assumption; actual refill cost depends on target alignment, width, and speculation.  
   **Fix:** handle these instruction classes separately, restrict folding to supported circumstances, and expose branch-refill sensitivity. [Arm TRM, §§3.3.1–3.3.3](https://documentation-service.arm.com/static/5fce431be167456a35b36ade)

7. **Minor — Region validation and unknown-instruction handling can silently accept invalid estimates.**  
   `chacha_ascon/tools/arm_cycles.py:294–299,334–339`.  
   Missing disassembly entries are priced at one cycle, `.word` entries would fall through as ALU instructions, extra measured intervals are accepted, and label indices are ignored. An extra marker can shift implementation labels while still producing plausible output. For the current ELF, I checked raw-disassembly sizes: **no missing/size mismatches**, and no data directives appeared in the sampled measured regions. The normal next-PC branch test is sound when the trace is complete and sizes are correct.  
   **Fix:** fail on unknown/directive PCs, require exact interval counts and sequential labels, and verify marker pairing explicitly.

8. **Minor — Marker subtraction is valid for the current core model, but not a constant flash correction.**  
   `chacha_ascon/tools/arm_cycles.py:276–292,337–342`; `chacha_ascon/bench/bench_arm.c:51–62`.  
   The alternating-interval selection is correct. In the existing binary, the empty interval contains `bx lr` and the second marker’s `bl`, totaling six modeled core cycles; subtracting it correctly removes those marker transfers. However, FlashART starts cold at the first marker, so that baseline includes cache misses unlike later marker intervals. Subtracting it globally biases flash estimates downward. Argument preparation and indirect-call overhead also remain inside the measured interval.  
   **Fix:** distinguish constant marker execution overhead from cache-dependent fetch effects, and describe results as the full harness call interval.

9. **Minor — Build changes can leave stale implementations in the tested or estimated binary.**  
   `chacha_ascon/arm/Makefile:40–42,57–69`.  
   Changing `OPT` or compile flags does not invalidate existing objects. The ascon-c rules also omit dependencies on shared headers outside each implementation directory. A subsequent successful test can therefore validate stale code rather than the intended configuration.  
   **Fix:** use configuration-specific build directories or flag stamps, generate header dependencies, and record compiler/build provenance with each result.

**Correctness checks that passed:** I found no concrete ChaCha20 algebra, round-count, in-place, tail, register-preservation, or counter-handling bug within the documented API contract. The assembly allocates 80 bytes including saved registers, restoring eight-byte stack alignment; its multiple/doubleword transfers address aligned stack/state memory. The `QRL` instructions do not update flags, so the loop’s `subs` survives to `bne`. Counter wrap is excluded by the public caller precondition. Unaligned single-word input/output accesses assume normal memory and unaligned trapping disabled.

The existing M4 test binary passed **16 implementations, zero skips, zero failures**. Registry traversal exercises every registered implementation on its applicable vector sets. Ascon-c symbol isolation also looks correct; the inspected combined object exports only its two renamed entry points.

**Verdict:** The reported numbers are defensible as provisional outputs of a disclosed model, not validated M4 speeds or estimates with a +0…+10% accuracy guarantee. Fix the core timing rules, enforce the correctness gate, rerun, and label the flash result as a fetch-only approximation unless its missing memory behavior is implemented and validated.
