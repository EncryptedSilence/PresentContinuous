1. **Medium — The stated comparison reverses the cycle error and understates some slowdowns.** `chacha_ascon/results/arm/m4-board.csv:28`, compared by matching implementation and message size with the model CSVs: `(board_cycles / model_cycles − 1)` ranges from **−1.53% to +16.82%** against the flash model. Most board timings are slower. At 4096 bytes, zero-wait cycle increases include opt32 **32.28%**, bi32 **30.21%**, armv7m **48.18%**, and bi32_armv7m **38.64%**. A 25–33% *throughput reduction* describes some of these results; calling that a 25–33% cycle slowdown is incorrect.

2. **Medium — This is not a controlled validation of the flash model on the measured executable.** `chacha_ascon/arm/Makefile:22–37` builds the model with soft float and ordinary alignment, but hardware with hard float and 16-byte function alignment. `nm` confirms different flash-line offsets: model `ascon_c_opt32_encrypt=0x18d8c`, board `0x08012530`; model `armv7m_encrypt=0x1e5ac`, board `0x08017cf0`. The fetch model explicitly depends on instruction addresses. Consequently, a discrepancy combines model error, generated-code differences, and placement effects; agreement does not establish ART-model accuracy, and excess cycles cannot be attributed solely to flash stalls.

3. **Medium — Firmware dependencies can silently reuse obsolete timing or clock code.** `chacha_ascon/arm/Makefile:136–142` uses `timing.h`, `system_init.c/.h`, startup assembly and `semihost.c/.h` without listing them as prerequisites. Change the clock setup or timing barriers, then run `make TARGET=m4hw board`: an existing ELF can remain “up to date,” and the old firmware runs while the CSV records the current source revision. The ELF hash identifies the binary but does not establish correspondence to the reported source.

4. **Medium — The parser does not enforce a complete, valid measurement.** `chacha_ascon/tools/m4_board.py:82–103` checks column counts but not the expected header, 48 unique rows, implementation/size coverage, numeric values, marker ordering, or checksum. Dropping one complete timing line still produces an accepted CSV. The clock check is also a substring test: I verified, without hardware, that `meas_status=10` and a garbage two-column CSV are accepted. Additionally, failure before `os.replace()` leaves the previous CSV intact (`:123–145`), contrary to the “stale CSV is never left looking current” claim at `:13`.

5. **Low — The KAT cap is disclosed, but the “complete” gate claim is false.** `chacha_ascon/tests/test_ca.c:134,330` skips eight records per implementation: **128 implementation-record runs** overall. The CSV honestly records that. However, `ca_fw_main.c:5–9,119` claims every vector passed. A defect triggered only at 8192 bytes or above can pass this board gate. The count checks (`test_ca.c:172,348`) still detect missing records, but establish only records encountered—including skipped records—not vectors executed or validated. Ascon skips even field validation after `Len`. `KAT_LINE_MAX=4096` is adequate for the current files’ longest line, 1029 characters, and overflow fails closed.

6. **Low — One-cycle subtraction does not isolate the implementation’s execution cost.** `ca_fw_main.c:133–137,157–159,174–177` calibrates adjacent counter reads, whereas actual regions include argument setup, function-pointer loads and dispatch. Disassembly confirms these instructions between timestamps; Ascon also includes the `im->enc` branch. The model harness has its own surrounding instructions and marker subtraction (`bench/bench_arm.c:60–62,73–75`). This is reasonable call-level benchmarking, but the boundaries are not instruction-identical, particularly relevant at 64 bytes.

The supplied ELF hash matches the CSV. The timed APIs, lengths, payload accounting and input patterns match the model harness. Heap allocation occurs outside timing; board buffers are eight-byte aligned and model buffers are sixteen-byte aligned, with identical strides—no demonstrated unaligned-access penalty.

All 48 rows having median equal to minimum is plausible for deterministic execution with interrupts masked and warm code. It proves neither that all seven trials were equal nor repeatability across boots or layouts. The evidence supports warm-call performance for this particular SRAM-buffer firmware configuration; it does not establish general product performance or isolate the cause of model discrepancies.
